Part I — Project Overview
1. Purpose & Objective
Xebia LMS is an enterprise-style Learning Management System supporting three roles — Admin, Trainer/Teacher, and Student — across course authoring, batch/cohort management, assessments, events, and learning analytics. The codebase combines fully implemented Spring Boot backend modules with a React frontend that, for some features, still falls back to local (browser) state when the corresponding API is not enabled. This document describes the backend as it exists in source today, not an idealized target state.

8. Authentication & Security Model
Xebia LMS uses a header-based mock authentication scheme rather than JWT or session tokens. Every request passes through two filters in the security chain:
TenantFilter — requires an X-Organization-ID header (UUID). This value scopes every query to a tenant/organization, enabling multi-tenant data isolation.
MockAuthenticationFilter — trusts two additional headers at face value:
X-User-Id — identifies the calling user (e.g. load-tester)
X-User-Role — identifies the calling role (e.g. ADMIN), which determines authorization scope
X-Organization-ID: 123e4567-e89b-12d3-a456-426614174000X-User-Id: load-testerX-User-Role: ADMIN
/api/auth/login and Swagger paths are public; all other endpoints expect the three headers above. This is explicitly not production-grade security — there is no cryptographic verification of identity, no JWT, and no signature checking. The project’s own internal documentation lists this as the top production blocker, alongside frontend-seeded credentials, plaintext demo password comparison, and wildcard CORS.

11. Known Limitations & Roadmap
Documented directly by the project maintainers as current production blockers and near-term priorities:
Replace mock header authentication with real identity + role enforcement (JWT/RBAC)
Frontend-seeded credentials and plaintext demo password comparison need hardening
Wildcard CORS needs tightening
Teacher backend authentication path is incomplete
Backend Batch/Join-Code/Subject module is still frontend/localStorage-only in places
Assessment submissions/grading records need normalization (currently serialized through student tasks)
File uploads are local-disk only (backend/uploads/) — no object storage yet
No isolated/sandboxed coding-assessment runner yet (JS test execution happens client-side)
